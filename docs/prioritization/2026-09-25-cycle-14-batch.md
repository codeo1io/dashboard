### B1 — rm-191: Aggregator cold-start in-flight degradation contract (track: reliability, priority: 59.0, status: candidate)

- **Problem**: between `start()` and the first refresh completing, `getSnapshot()`
  returns `{repos: [], staleBanner: false}` (`src/github/aggregator.ts:823-830` at
  cfe26c4) — authoritative-looking fresh-empty. `start()` gates interval installation
  behind `await refresh()` (`:833-843`) and no transport is time-bounded (zero
  `timeout`/`AbortSignal`/`signal` across `app-client.ts`/`installations.ts`/
  `metadata.ts` Octokit constructions), so a stalled serial first walk (undici default
  ~300s/hop across N repos) yields minutes-to-hours of false-fresh empty with no retry
  ticks. Contrast: a FAILED first refresh already banners via `markSnapshotStale()`
  (`:647-656`) — only the in-flight window is uncovered. PR #140's warm-empty guard
  protects last-good states only; cold start has no last-good.
- **Acceptance**: (1) while a refresh is in flight, `getSnapshot()` never returns
  `staleBanner: false` with empty `repos` — an explicit in-flight/degraded marker or
  `staleBanner: true`; (2) every GitHub transport call is time-bounded (constructor
  `request.timeout` or per-call `AbortSignal.timeout`, configurable via the existing
  options seam, default ≤30s); (3) interval installation no longer remains blocked
  behind an unbounded first refresh (bounded by the timeout, or installed
  independently); (4) a stalled first request trips the existing FAILED-refresh
  stale-banner path. **Evidence**: aggregator unit tests pinning (a) in-flight snapshot
  shape at cold start, (b) timeout→FAILED→banner, (c) interval installed without a
  completed first refresh; grep showing timeout wiring in all three transport modules;
  PR #140 interleave rebase note in the landing PR body.
- **Why not dup**: rm-112's halves (absence entries, warm-empty) are PR #140's payload;
  this is the cold half, unowned anywhere (verified against open PRs).

### B2 — rm-194: Redaction single-char token boundary (track: security, priority: 41.0, status: candidate)

- **Problem**: `redactRepoIdentityFromText` filters its `[owner/name, owner, name]`
  token list with `token.length > 1`, dropping GitHub-legal 1-char owner/repo tokens
  from log scrubbing entirely (`src/github/aggregator.ts`, redaction core). The
  property suite's `nameArb` (`test/aggregator-invariants.property.test.ts:27`,
  `/^\w[\w.-]{1,30}$/`) enforces min length 2, so the suite structurally cannot catch
  the class. The `>1` filter exists to avoid mangling prose — the correct fix is
  word-boundary-anchored replacement, not length gating.
- **Acceptance**: boundary-anchored (`\b`) replacement covers tokens of length ≥1
  without substring mangling of adjacent prose; `nameArb` widened to min length 1;
  regression test with a 1-char owner and 1-char repo name proving both tokens are
  scrubbed from a sample log line while non-boundary substrings survive. **Evidence**:
  the boundary test green; property suite still green with widened arb.

### B3 — rm-195: Aggregator/shutdown lifecycle re-entry hardening (track: reliability, priority: 29.0, status: candidate)

- **Problem**: `start()` has no re-entry guard (double-start leaks a duplicate refresh
  interval; `:833-843`), `stop()` clears only `intervalHandle` (`:851-856`), and
  `src/shutdown.ts`'s header claims "Idempotent at the process level" with no latch in
  `installShutdownHandlers` — the claim is OS-signal-race-true but not code-true.
- **Acceptance**: `start()` re-entry is a documented no-op (returns existing lifecycle)
  or explicit throw — never a second interval; `stop()` idempotent and clears all
  timers; `shutdown.ts` claim matches behavior (latch added or claim reworded to what
  is actually guaranteed). **Evidence**: double-start/double-stop unit tests; doc-code
  parity in the header.
